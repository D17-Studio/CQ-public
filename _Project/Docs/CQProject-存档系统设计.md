**目标：打通"打歌出分 → 存档 → 读取回显"链路。**

- 服务对象：最佳成绩展示（本轮）；难度解锁（设计文档决策 3，数据来源本身待定，本轮**不做**）

## 二、设计取向（四条原则，与 SaveManager 路线的根本分歧）

1. **按需裁剪，不预先通用化**——分数存档就做分数；通用层等第二个消费方（玩家配置）真正出现再抽。
2. **可变状态不出门**——外部拿到的只有只读快照；改数据必须走显式命令方法。
3. **磁盘格式简单且可自愈**——一个可读、可备份、坏了能保底重来的文件。
4. **身份与存储解耦**——曲目身份是 JSON 里的数据字段，不是文件名/目录名。

## 三、数据与存储形态（scores.json）

**单文件、按"域"分文件**：一个 `scores.json` 装全部记录（路径 `Application.persistentDataPath` 下），不给每个 key 单独文件。

理由：写入频率 = 每打完一局一次，数据量 = 每谱面几十字节。这个量级下"每 key 一文件"的增量写没有收益，却付出 key 变文件名（清洗非法字符、防空 key 撞车）的代价；单文件全量重写是更优解，并带来两个红利：

- **key 不进文件系统**——索引口径（见"八"）只是 JSON 内字符串字段，命名格式无任何约束；
- 好备份、好排查（玩家发一个文件即可）、开发期删文件即重置。

单点损坏风险（一坏全丢）由"原子写 + 坏档保底"抵消（见"五"）。

**格式**（JsonUtility 约束：公开字段、对象作根、无字典——所以用 List-of-entries 技巧）：

```csharp
// 磁盘根：对象包一层（JsonUtility 要求），Version 是廉价的迁移钩子
[Serializable] class ScoreArchiveData { int Version; List<ScoreRecord> Records; }

// 记录：身份 = 单个字符串 Key（拼接口径由索引工具类负责——为 trackid + 难度之外的特征留扩展；Key 格式发布后视同稳定）
[Serializable] class ScoreRecord { string Key; int BestScore; bool IsFullCombo; }  // IsFullCombo = 曾经达成（永不熄灭）

// 对外只读快照——Exists：字典里有条目 = 打过（免费获得"没打过 vs 打过 0 分"的区分）
readonly struct ScoreView { bool Exists; int BestScore; bool IsFullCombo; }
```

**文件外壳（防手改，2026-10-14 定案）**：磁盘文件 = `{ "Payload": "<ScoreArchiveData JSON 的 Base64>", "Mac": "<HMAC-SHA256 签名>" }`——不能直读；加载先验签、后解析；不符按坏档处理（见"五"）。

## 四、API 与规则

```csharp
class ScoreArchive
{
    ScoreArchive(string filePath);              // 构造即加载（异常 → 备份坏档 + 空档启动）
    ScoreView GetBest(string key);              // 纯查询，绝不交出内部对象引用
    void RecordScore(string key, int score);    // 哑存储：传什么记什么，立即原子落盘
    void RecordFullCombo(string key, bool isFullCombo); // 哑存储：传什么记什么
}
```

- **取优判断住结算流程，不住存档类**（用户提案并定案 2026-10-14）：`ResultPresenter.OnTrackEnded` 先 `GetBest` 拿旧值 → 比较 → 改善才 `RecordScore` / 首次达成才 `RecordFullCombo`。理由：规则属业务层；结算处本来就要读旧值（NEW BEST 展示、将来"上次最佳"与解锁判断同现场）；单写点下"不变量 by construction"的收益不抵可见性。防呆补偿：写口契约写进 XML 注释、规则收敛在结算处一个具名方法；出现第二个写点时再考虑收回类内。
- **结算处规则**（2026-10-14 定案；两写口互相独立、各自独立落盘）：
  ```csharp
  var old = _archive.GetBest(key);
  if (!old.Exists || score > old.BestScore)
      _archive.RecordScore(key, score);     // 相等不算新纪录，不写
  if (fc && !old.IsFullCombo)
      _archive.RecordFullCombo(key, true);  // 只在首次达成时写入（"永不熄灭"靠这条守卫）
  ```
- **FC 语义 = 曾经达成**（用户拍板 2026-10-14）：FC 一旦点亮永不熄灭（成就语义）；由 `RecordFullCombo` 独立写口承载、不触碰分数——不存在"未破纪录但首次 FC 要回写旧分数"的捆绑。
- **落盘 = 立即（写透）**：写口内部改完即保存（原子写），外部不存在"忘了落盘"的可能。写入失败 → 记日志，内存状态仍正确，下次成功写入全量补写。
- **有效成绩口径**：自然曲终才写（`TrackEnded` 仅自然终触发，现有守卫已如此）；中途暂停返回不写。
- **防呆三条**（取代现有 SaveManager 的三个坑）：没有脏标记契约（写透）；不泄漏可变引用（快照出门）；查询零副作用（不"读即创建"）。
- **全 Perfect 不存标志**：`AllPerfect ⇔ Score == 1,000,000`（`ScoringSystem.FullMarks` 且 P 阈值同为 1,000,000），由分数判断。
- **索引 Key**：`ScoreKeys.Of(track, chart)`（唯一落点）= `MusicTitle.Trim() + "_" + 难度映射表代号 + "_" + 存档签名`（签名为 track 级 `ArchiveSignature`，可空，空保留末尾 `_`）；完整口径见"八"（存档本体不关心 Key 怎么来）。

## 五、鲁棒性

- **原子写**：先写 `scores.json.tmp` 再替换正式文件——防"写一半被杀进程/断电"，这是唯一真会吃掉分数的场景。
- **坏档保底**：读 + 解析全程 try/catch（已核实 JsonUtility 对损坏文本会**抛异常**而非回 null）→ 坏文件改名留证（不删）→ 警告 → 空档启动。
- **防手改 = Base64 + 签名（轻量档，2026-10-14 定案）**：payload = ScoreArchiveData JSON 的 Base64 编码（不能直读）+ 文件级 `HMACSHA256(密钥, Base64 串)` 签名。加载先验签、后解析，不符 = 走坏档路径（备份 + 重置）。**威胁模型（2026-10-14 用户明确）= 只防"手痒改"两档：①打开见乱码不折腾 ②会解码、改完编码回去——被签名识破。反编译、内存修改 = 视为黑客，接受；密钥从公开库同步排除（`sync-public.sh` 的 EXCLUDED_FILES 加 `Assets/Features/Persistence/Scripts/ScoreArchiveKey.cs`——机制公开、密钥值不进公开库）；真防护 = 服务端校验，联网功能出现时再议。** 要点：① 验签输入用文件里 `Payload` 原文（Base64 串本身），禁止"解码/解析后再序列化再验" ② 密钥 = 单串随机常量（**不拆分**——拆分只为防"公开库明读"，改为排除后已无防护对象，代码混淆花活不投入），落独立文件 `ScoreArchiveKey.cs`（仅存密钥；文件若迁移，同步排除清单须跟着改）③ 发布后不可更改（改 = 全部旧档验签失败被重置；alpha 期除外）。
- **零判断与校验责任**（2026-10-14 定案）：存档类不做任何输入校验与业务判断（传什么记什么）；仅在加载时跳过 Key 为空的脏条目；取优、数值合法性等责任全在调用方（单写点，已接受）。
- **首次运行 / 无存档（2026-10-14 补）**：文件不存在 = 正常状态而非坏档——空档启动、不产生备份；纯查询零副作用（只浏览不写盘）。**磁盘状态三分支**：不存在 → 空档；损坏 / 解析失败 → 坏档路径（备份 + 空档）；验签失败 → 同坏档路径。UI：`Exists=false` 显示占位（文案步骤 4 定）。
- **首写分支（实现要点）**：原子写的替换环节要处理"目标不存在"（`File.Replace` 要求目标已存在）——首写走 move 路径。
- **写失败重试**：无需专门机制——每次 `Save` 全量序列化内存状态，**下一次成功写入天然补写**此前失败的内容（写透 + 全量）；失败仅记日志、不崩溃（2026-10-14 实施时简化：原"失败标志"方案实为冗余，已裁）。
- **旧版本兼容立场**：尽力解析——缺字段回落默认值（对分数无害）、更高 Version 也尽力解析（alpha 不拦截）；字段改名 = 静默丢值（已知接受）。
- **接受的边界（2026-10-14 审视定案）**：孤儿记录不清理（曲目改名 / 删除后旧记录留存，将来需要再加工具）；多实例同跑 = 后写覆盖（单机单实例）；不做"上一份好档"轮转（原子写已防写坏，分数可再生，成本大于收益）。

## 六、与现有 SaveManager 的关系

**本任务不引用 SaveManager**，分数走 `ScoreArchive` 独立文件。评估要点（2026-10-14 讨论，供将来去留判决参考）：

- 现状零业务消费方（除 README 外无人使用），本任务是它的潜在首个客户——但接口形态不匹配（见下）。
- 已知问题：① 脏标记契约靠使用纪律（`Get` 返回可变引用，改后须手动 `SetDirty`，编不过也查不出）② 坏档兜底的 null 检查疑似拦不住真实损坏（`FromJson` 抛异常路径）③ key 零校验（空 key 全部共用一个文件）④ `typeof(T).Name` 作目录名（同名类型碰撞；类型改名 = 旧档静默失联）。
- **去留判决留到第二个通用需求出现时**（届时按"二、设计取向"改造或替换）；本轮不为它打补丁。

## 八、索引口径（2026-10-14 定案；2026-11-13 修订）与其余待定

**索引口径（2026-11-13 修订）**：`key = MusicTitle.Trim() + "_" + 难度代号 + "_" + 存档签名`

- **存档签名 = track 级 `ArchiveSignature`**：官谱 = `OfficialTrackInfo.ArchiveSignature`（SO 手填，可空）；自制谱 = 留空。签名为空时保留末尾 `_`（不省略），键形如 `曲名_Dif0_`。
- **身份政策（2026-11-13 修订）**：官谱 = 乐曲名 + 可选签名（标题稳定；重排 `001_` 编号也不受影响）；自制谱 = 签名留空（同名自制曲会共用存档键，接受此限制）；任何来源要冻结 / 防撞 = 手填签名。
- **格式变更影响**：旧键（`曲名_DifN` / `ArchiveId_DifN`）全部失联；alpha 期不迁移、不兼容（2026-11-13 用户定案）。
- **难度代号 = 映射表字面量**（`ScoreKeys.DifficultyCode`）：与枚举成员名 / 顺序解耦——枚举随便改名、重排、插新难度都不影响旧档；字面量现为 `Dif0`~`Dif3`（以 `ScoreKeys` 代码为准），是存档契约，发布后不可改（与密钥同类性质，已写进唯一落点注释）。
- **脏字符不清洗**：key 只是 JSON 字符串（单文件设计红利），清洗反而制造碰撞（`PROJECT ▽ DIGITOPIA` 洗成 `PROJECT_DIGITOPIA` 可能与另一首真撞键）；仅 `Trim()` 防首尾空白手滑。
- 落点 = `ScoreKeys.Of(track, chart)`（唯一落点，见"七"步骤 2）。

其余待定：

- 难度解锁的数据来源（与《主菜单UI框架设计》决策 3 关联）——本轮不做。
- `ScoreArchive` 装配绑定点——已定案并落地：独立 `ScoreArchiveInstaller`（2026-10-14，见"七"步骤 3）。

分数存档的第二个消费方是玩家配置（流速 / 延迟 / 音量等，对应主菜单设计文档中的 `SettingsService` 数据层）。方向结论（2026-10-14 讨论；**存储层已于 2026-10-14 落地**——`PlayerConfig` / `PlayerConfigStore` / `PlayerConfigInstaller` 并入 `Features/Persistence/`，落地定案：不抽 JsonFile 共享层（债）、明文 JSON 不签名、首期字段 = 流速 + 偏移（音量等后续按需加）；消费方接线未动工——2026-10-15：接线成为下一任务，接线点 = `TrackPlayingInstaller` 的硬编码 `new NotePositionCalculator(1000, …)` 改读 `ScrollSpeed`、偏移应用点 = `TrackController.GetTrackTime()` 的临时 `-70`（与 `InputOffsetMs` 合并方式待定）、设置面板形态见《主菜单UI框架设计》决策 1/5）：

- **访问习惯不同**：单条数据、设置页高频改、打歌处处读 → 策略 = 改内存即时生效、**检查点落盘**（设置面板关闭/应用 + `Application.quitting` 兜底），绝不为滑块每帧落盘。
- **形态**：`PlayerConfigStore`（纯 C#，DI 绑定，同 `ScoreArchive` 模式）+ `PlayerConfig`（`Version / ScrollSpeed / InputOffsetMs / ...`）；脏标记藏在 store 内部（setter 自动标，外部想忘也忘不掉）——这是"脏标记"机制唯一合理的客户。
- **演化坑**：新增字段对旧档回落 0——对分数无所谓，对流速是灾难（0 倍速）→ `Load` 后需"缺省修正"或按 `Version` 迁移。
- **单玩家假设**：不做多档案；键位重绑现有 `customBindings.json` 由 InputSystem 自管，并入与否另行讨论。
- **JsonFile 层**：分数与配置共享的只有文件机制（读入 / 坏档保底 / 原子写 / Version），到时抽一个 `JsonFile.Load<T> / Save<T>` 静态助手——**通用的是文件机制，不是数据 API**（现有 SaveManager 的错误轴：把"类型 + key + 可变对象注册表"通用化了）。
