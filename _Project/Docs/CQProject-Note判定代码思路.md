# Note判定代码思路

# Note种类

- Dot
- Dash
- Mute
- Tune

# 判定逻辑

### Dot：

常规头部判定池、完成判定后直接销毁

### Dash：

常规头部判定池，完成头部判定后**存储判定结果**并**进入长按判定池**

在长按判定池中的行为：

1. 到达时间时，判定为“完成”并结算存储的结果
2. 松开按键时，判定为miss并销毁

### Mute：

Mute头部判定池

进入长按判定池之后，行为与Dash一致

### Tune：

在相应的Dash生成时，加入Tune判定池，判定完成后销毁并结算分数

在相应的Dash判定为miss时，自身立即判定为miss

在自身判定为miss时，将相应的Dash判定为miss

# 程序实现思路

## 判定池：

不同的判定池管理不同方式的判定，并且各判定池之间相对无关联

- 常规头部判定池：Dot、Dash生成时所处的判定池
- Mute头部判定池：Mute生成时所处
- 长按判定池：Dash、Mute完成头部判定后加入的池子
- Tune判定池：Tune生成时所处

### 判定池行为：

- 常规头部判定池：点击判定，同轨道一次点击只能判定**一个**Note，超出时间的Note判Miss
- Mute头部判定池：按住及松开的一段时间内可进行判定，超出时间的Note判Miss

- 长按判定池：将没有长按的轨道上所有Note判Miss，达到结束时间的Note进行结算

- Tune判定池：与常规头部判定池判定逻辑相同

  （需要注意的是，一次点击可以判定一个常规头部判定池的Note与Tune判定池的Note

### Note之间信息传递问题

先前说过，各判定池之间相对无关联，不过因为Tune键的存在，所以不同池子之间的判定会产生关联性。

再次申明一次规则：

1. 一个Dash与多个Tune关联
2. Dash判miss时，所有关联的Tune都需要判miss
3. Tune判miss时，与其关联的Dash需要判miss

需要注意防止无限递归，可以先“销毁”自身，再进行连锁判定。
